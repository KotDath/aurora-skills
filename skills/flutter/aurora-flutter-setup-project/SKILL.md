# Set up an Aurora Flutter project

The helper requires Python 3.10+ and PyYAML for parsing existing `pubspec.yaml` files. Use `uv run <skill-directory>/scripts/setup_project.py ...` to resolve the declared dependency, or `python3` from an environment with PyYAML installed. It uses safe YAML parsing; indentation is not a project-type signal. Missing parser support is reported before platform generation.

When continuing from `setup-aurora-skills`, reuse its project card, SDK choice, plugin implementation, and requested action without restarting the interview. This skill also works directly; onboarding is not a prerequisite. Read the selected project's existing agent instructions and local SDK record first.

Use the Aurora Flutter fork, not an upstream `flutter` found on `PATH`. For first-time setup, require a Flutter SDK path explicitly supplied by the user; use a path already supplied in the conversation without asking again. The bundled script currently accepts only executables whose machine-readable channel contains `aurora`, and records the SDK root as `flutter` in the project-root `.aurora/sdk.json`. This is a helper compatibility check, not an official guarantee of fork identity: inspect provenance and Aurora command/template support as well. If an otherwise verified distribution uses a different channel, report the helper limitation; do not relabel the SDK, substitute another installation, or claim that channel naming proves it is upstream. Once that value exists, treat it as authoritative: do not switch to another SDK through `PATH`, an environment variable, or an incidental command argument. If no Flutter SDK path is known, ask for it.

Run `scripts/setup_project.py --flutter-sdk <sdk-root> --output <directory>` for a new app. Add `--template plugin`, `plugin_qt`, or `plugin_ffi` when the user wants a plugin of that kind; the normal plugin template uses method channels. Pass `--org`, `--project-name`, and `--description` when known. Pass `--no-pub` for scaffolding unless dependency resolution is part of the request. For an existing Flutter project, pass `--existing` only when adding platform support was requested. Preserve an explicitly chosen plugin implementation with `--template`; otherwise the script distinguishes apps from method-channel plugins. Use `--record-only --existing` for workflow-only setup, including when Aurora support is not present yet; that mode must not generate platform files or resolve packages. The script records only the Flutter SDK; it does not discover, invoke or add sfdk. Existing unrelated SDK configuration is preserved. Read `--help` for exact flags.

Honor the agreed destination, including the current directory when explicitly requested. For an unspecified output, use an app-named child directory of the current directory. New projects require a new/empty directory or one containing only `.git`; do not overwrite other content or bypass the check by generating elsewhere and copying files. When no organization was given, `ru.example` is a temporary placeholder; tell the user. Do not invent a real organization identity.

After successful creation or recording, the script writes `.aurora/sdk.json` and ignores that local file in Git, preserving other config keys. It updates only `flutter` (Aurora Flutter SDK root), preserving other keys without probing their executables. Read `flutter` on every later turn and use its `<sdk-root>/bin/flutter` for every project operation, including `pub add`, `pub get`, building, and running. A conflicting Flutter SDK path is an error unless the user explicitly chose to change it. For that requested change, pass `--existing --record-only --replace-sdk --flutter-sdk <new-root>`; the script validates the replacement before saving it, without regenerating the project. No additional confirmation is needed for an already explicit SDK-change request. The setup script migrates an existing `.aurora-flutter-sdk` marker to this format. After generation, check `pubspec.yaml` and the Aurora platform files; after record-only mode, confirm the config changed and application files did not. Report the project location, actual action, effective SDK path, and Flutter version. Platform generation does not implement or test an upstream plugin port. Build or run the app only when requested.

For an existing plugin, the SDK may generate native files while preserving `pubspec.yaml` unchanged. Inspect its output and the resulting platform registration before claiming Aurora support was added. Add the matching Aurora platform declaration when platform integration was requested: derive method-channel/Qt entrypoints and headers from the generated implementation; FFI uses `ffiPlugin: true`. Preserve other platforms and project metadata. If integration requires additional packages, use `aurora-flutter-add-dependency` instead of inserting dependency declarations by hand. Report remaining Dart/native porting and testing work separately from the generated skeleton. Record-only mode must not make these integration edits.

To add packages after setup, use the separate `aurora-flutter-add-dependency` skill. Its manually maintained `scripts/checked-dependencies.yaml` is the dependency acceptance list; do not duplicate that list here.
